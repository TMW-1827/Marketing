# Навчальний портал ТМ «Трускавецька»

Внутрішній портал для навчання працівників: 14 розділів про бренд і продукт,
каталог із 18 позицій, калькулятори палет і націнки, підсумковий тест
із сертифікатом, звіт для керівника.

Веб-версія — PWA: працює офлайн і ставиться на початковий екран телефона.
Той самий код пакується в додатки для Android та iOS через Capacitor
(див. «Мобільні додатки»).

## Швидкий старт

```bash
npm install
cp .env.example .env.local   # необов'язково, див. «Бекенд»
npm run dev                  # http://localhost:5173
```

Без `.env.local` портал запуститься в **автономному режимі**: усі матеріали
доступні без входу, прогрес зберігається лише в цьому браузері.

## Три режими роботи

Режим визначається змінними оточення й перемикається сам:

| Режим        | Коли вмикається                    | Що відбувається                                                        |
| ------------ | ---------------------------------- | ---------------------------------------------------------------------- |
| **backend**  | задані ключі Supabase              | Справжні акаунти, прогрес синхронізується між пристроями, звіт із бази  |
| **demo**     | ключів немає, `VITE_DEMO_AUTH=true` | Вхід за вбудованими тестовими акаунтами, усе локально                   |
| **open**     | ключів немає, прапорця немає        | Без входу взагалі, матеріали одразу                                     |

Демо-режим потрібен, щоб перевіряти вхід, ролі й адмінку **до** підключення
бази. Акаунти вбудовані в збірку (`src/features/auth/demoAccounts.ts`),
паролі відкриті — це навмисно, бо перевіряються самі сценарії, а не безпека.
Реєстрація в цьому режимі вимкнена, адмінка показує зразок даних із явним
попередженням, що цифри вигадані.

Пошта й паролі демо-акаунтів збігаються з `supabase/seed/test_accounts.sql`,
тож після підключення бази ті самі облікові записи працюватимуть далі.
Щойно з'являються ключі Supabase, демо-акаунти вимикаються самі.

У демо-збірці (`npm run build:demo`) режим вмикається автоматично.

## Команди

| Команда              | Що робить                                          |
| -------------------- | -------------------------------------------------- |
| `npm run dev`        | Режим розробки з гарячим перезавантаженням         |
| `npm run build`      | Перевірка типів + продакшн-збірка у `dist/`        |
| `npm run build:demo` | Один самодостатній HTML у `dist-demo/` для показу  |
| `npm run preview`    | Локальний перегляд зібраного порталу               |
| `npm run typecheck`  | Тільки перевірка типів                             |
| `npm run smoke`      | Наскрізні перевірки в браузері (потрібен preview)  |
| `npm run smoke:auth` | Перевірки входу й ролей (потрібен `build:demo`)    |

Для `npm run smoke` один раз поставте браузер: `npx playwright install chromium`.
Той самий набір можна прогнати проти вже опублікованої збірки — вкажіть адресу:
`SMOKE_URL=https://tmw-1827.github.io/marketing/training-portal/ npm run smoke`.
`build:demo` задає змінну оточення через синтаксис Unix — на Windows
скористайтеся `cross-env` або задайте `BUILD_TARGET=demo` вручну.

## Бекенд

Акаунти працівників, синхронізація прогресу між пристроями й звіт для
керівника працюють на Supabase.

1. Створіть проєкт на [supabase.com](https://supabase.com).
2. Виконайте `supabase/migrations/0001_init.sql` у SQL Editor проєкту.
3. Скопіюйте `.env.example` у `.env.local` і заповніть:

   ```
   VITE_SUPABASE_URL=https://<ваш-проєкт>.supabase.co
   VITE_SUPABASE_ANON_KEY=<anon public key>
   ```

4. Призначте адміністратора — у SQL Editor:

   ```sql
   update public.profiles set role = 'admin'
   where id = (select id from auth.users where email = 'keruvnyk@truskavetska.com');
   ```

### Тестові акаунти

Щоб одразу перевірити вхід, ролі й звіт, виконайте
`supabase/seed/test_accounts.sql` після міграції. Він створює двох
підтверджених користувачів і трохи прогресу, щоб звіт не був порожнім:

| Роль          | Пошта                         | Пароль       |
| ------------- | ----------------------------- | ------------ |
| Працівник     | `pracivnyk@truskavetska.test` | `Test1234!`  |
| Адміністратор | `kerivnyk@truskavetska.test`  | `Admin1234!` |

Домен `.test` не існує, тому листи нікуди не підуть. Перед відкриттям
порталу для працівників видаліть ці акаунти — команда в кінці того ж файлу.

Після цього вхід стає обов'язковим, а адміністратор бачить розділ
**Звіт про навчання**: скільки розділів пройшов кожен працівник, який бал
на тесті, скільки було спроб і коли була остання активність.

### Що зберігається

| Таблиця         | Призначення                                                   |
| --------------- | ------------------------------------------------------------- |
| `profiles`      | Ім'я, посада, регіон, роль (`employee` / `admin`)              |
| `progress`      | Позначені розділи, найкращий бал, дата успішного складання     |
| `quiz_attempts` | Кожна спроба тесту — для звітності, а не лише останній результат |

Доступ обмежують політики RLS: працівник бачить і змінює лише свої рядки,
адміністратор має доступ на читання до всіх. Спроби тесту не можна
відредагувати заднім числом.

### Офлайн і синхронізація

Прогрес завжди спершу пишеться локально, потім вирушає на сервер. Якщо
зв'язку немає, зміни лишаються в черзі й підуть автоматично, щойно
з'явиться мережа — у профілі при цьому видно позначку «Не синхронізовано».
При вході з іншого пристрою локальний і серверний стани **об'єднуються**:
позначені розділи додаються, бал береться найкращий, нічого не губиться.

## Структура

```
src/
  content/          Курс: розділи як типізовані блоки, а не HTML
    course.ts       Збірка курсу; сюди ж додаються нові курси
    sections/       По файлу на розділ
  data/             Незмінні дані: SKU, тест, заперечення, глосарій
  types/            Моделі контенту й каталогу
  lib/              Логіка без UI: розрахунки, пошук, формати, сховище
  components/       Спільні компоненти: рендерер блоків, навігація, пошук
  features/         Каталог, калькулятори, тест, прогрес, авторизація, адмінка
  styles/           Токени бренду й компонентні стилі
supabase/migrations Схема бази з політиками доступу
scripts/            Генератор іконок, наскрізні перевірки
```

### Як додати матеріал

**Новий розділ** — файл у `src/content/sections/` і рядок в `course.ts`.
Розділ описується блоками (`card`, `note`, `table`, `list`, `stats`…),
які рендерить `components/BlockRenderer.tsx`. Пошук індексує розділ
автоматично: текст витягується з блоків, окремо нічого прописувати не треба.

**Новий курс** — такий самий об'єкт `Course` і реєстрація в `COURSES`.
Модель даних до цього готова; знадобиться лише екран вибору курсу.

**Новий інтерактивний модуль** — компонент у `features/` та ім'я в реєстрі
`features/widgets.ts`. У контенті він підключається як
`{ kind: 'widget', widget: 'назва' }`, тому самі розділи лишаються
серіалізовними даними — їх можна перенести в базу чи CMS без переписування.

## Публікація вебу

`npm run build` кладе статичні файли в `dist/`. Шляхи всередині відносні,
тому збірка працює з будь-якого підкаталогу — і на GitHub Pages, і в нативній
обгортці Capacitor.

Портал опублікований за адресою:

```
https://tmw-1827.github.io/marketing/training-portal/
```

**Зараз він оновлюється вручну.** Зібрані файли лежать у репозиторії в
каталозі `training-portal/`, поруч із `equipment-portal/` — так само, як
влаштований сусідній портал. Після зміни коду:

```bash
cd training-portal-src
npm run build
rm -rf ../training-portal && cp -r dist ../training-portal
git add ../training-portal && git commit && git push
```

Щоб позбутися ручного кроку, у репозиторії лежить
`.github/workflows/deploy-pages.yml`: він збирає портал сам і публікує разом
зі звітами та сусіднім порталом. Для цього поставте Settings → Pages →
Source: GitHub Actions. Нічого не зламається — workflow викладає весь сайт,
усе лишається за тими самими адресами.

Якщо портал має працювати з акаунтами, додайте в Settings → Secrets and
variables → Actions два секрети: `VITE_SUPABASE_URL` і `VITE_SUPABASE_ANON_KEY`.
Без них збірка теж пройде — портал працюватиме автономно.

Портал закритий від індексації (`robots`, `noindex`), як і решта матеріалів
у репозиторії. Але адреса **публічна**: хто знає посилання — той відкриє.
Поки немає бази, вхід не запитується. Не публікуйте тут нічого, чого не
можна показувати за межами компанії.

## Мобільні додатки

Веб уже написаний з розрахунку на нативну обгортку, тож окремого застосунку
писати не доведеться:

- маршрутизація на хешах і відносні шляхи — працює з `file://`, де серверного
  роутингу немає;
- шрифти та іконки в бандлі — жодних запитів до CDN;
- сховище за асинхронним інтерфейсом (`lib/storage.ts`) — підміна на
  `@capacitor/preferences` торкнеться одного файлу;
- безпечні зони, площа дотику 44 px, нижня панель вкладок, шторки замість
  модалок, підказки по дотику замість наведення.

Коли дійде черга:

```bash
npm i @capacitor/core @capacitor/cli @capacitor/android @capacitor/ios @capacitor/preferences
npm run build
npx cap add android
npx cap add ios
npx cap sync
npx cap open android                  # Android Studio
npx cap open ios                      # Xcode
```

`capacitor.config.ts` уже налаштований: ідентифікатор `ua.truskavetska.portal`,
кольори бренду, вимкнені власні відступи WebView на iOS.

Після цього лишається: замінити реалізацію `localStore` на Preferences,
підключити нативний сплеш-скрін і зібрати іконки під сторів
(`scripts/make-icons.py` дає базовий набір).
