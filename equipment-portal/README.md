# Портал обліку торговельного обладнання

Внутрішній портал для обліку, замовлення (передачі), ремонту та інвентаризації
торговельного обладнання (ТО). Реалізує процес, описаний у «Положенні про порядок
обліку та управління торговельним обладнанням» (вер. 0 від 05.07.2026) і у схемі
процесу з 14 кроків.

Портал є **прогресивним вебзастосунком (PWA)**: одна кодова база обслуговує
десктопну вебверсію та мобільну версію для Android та iOS — застосунок
встановлюється з браузера на головний екран, працює у повноекранному режимі
й доступний офлайн.

---

## Що вміє портал

### Облік обладнання (п. 2, 6, 7 Положення)
- Реєстр ТО з унікальними інвентарними номерами, серійними номерами, категоріями,
  вартістю, фотографіями та повною історією руху.
- Автоматична генерація наступного інвентарного номера, контроль унікальності,
  заборона передачі без номера.
- Статуси: *На складі, В дорозі, У клієнта, У дистриб'ютора, У ремонті, Повернено,
  На списанні, Списано* — перелік редагується в адмінці.
- Друк етикеток зі штрих-кодом **Code 39** (той самий код читає вбудований сканер).
- Імпорт залишків із CSV та експорт реєстру.

### Заявки на передачу (п. 3–5)
Повний маршрут: **заявка → погодження Комерційним директором → планування ВАП →
відвантаження складом → Акт приймання-передачі**.
- Три типи передачі: клієнту; дистриб'ютору; клієнту через дистриб'ютора
  (в Акті окремо зазначається канал поставки, п. 5.4).
- Універсальний Акт приймання-передачі формується в системі й друкується;
  без відмітки про підпис відповідального менеджера Акт оформити не можна (п. 5.5).
- Після оформлення Акта статус і утримувач ТО змінюються автоматично.

### Ремонт (п. 10)
Заявка від відповідального менеджера → призначення сервісної компанії менеджером
із трейд-маркетингу → передача в ремонт → завершення з Актом виконаних робіт,
вартістю та погодженням до оплати. Фото несправності, облік витрат за одиницею ТО.

### Переміщення, повернення, втрати, списання (п. 9, 11)
- Переміщення й повернення лише з посиланням на документ.
- Повідомлення про втрату / пошкодження / викрадення з фото; розслідування та
  рішення (повернення, ремонт, компенсація, заміна, списання).
- Документ на списання з комісією та затвердженням Комерційним директором.

### Інвентаризація — мобільний сценарій (п. 12)
- Сесії інвентаризації з охопленням, строком і прогресом за відповідальними.
- **Сканер інвентарного номера** — камера пристрою + `BarcodeDetector`
  (Code 39/128, QR, EAN). Там, де API недоступний (Safari на iOS), автоматично
  вмикається ручне введення номера — процес не блокується.
- **Фотофіксація** — знімок із камери, стиснення до 1280 px, зберігання в IndexedDB.
- **Геолокація** — координати порівнюються з обліковою адресою; перевищення
  допустимого радіуса автоматично позначає позицію як розбіжність.
- Експорт результатів інвентаризації в CSV для бухгалтерії (п. 12.4).

### Звіти та контроль
- **Щомісячний звіт** про місцезнаходження (п. 8) з розсилкою сповіщень
  відповідальним менеджерам і експортом.
- Аналітика парку: категорії, статуси, міста, відповідальні, вартість.
- **Контроль строків**: не внесено місцезнаходження понад 10 робочих днів (п. 6.1),
  немає підтвердження понад рік (п. 12.1), заявки й ремонти без реакції.
- Витрати на ремонт із часткою від первісної вартості.

### Адміністрування
- Користувачі: створення, редагування, блокування, видалення, скидання пароля.
- Права доступу: 28 дозволів, 7 ролей за матрицею RACI + індивідуальні
  розширення та відкликання прав для конкретного користувача.
- Довідники: контрагенти й торгові точки (з координатами), категорії, склади,
  сервісні компанії, статуси ТО.
- Налаштування нормативів (строки з Положення, радіус геолокації, вимоги до
  фото/геолокації під час інвентаризації).
- Журнал аудиту та резервні копії (експорт/імпорт JSON).

## Ролі та права

| Роль | Основна зона відповідальності |
|---|---|
| Адміністратор системи | Повний доступ, користувачі та довідники |
| Бухгалтерія | Оприбуткування, контроль даних, інвентаризація, списання |
| Комерційний директор | Погодження заявок, рішення за інцидентами, затвердження списання |
| Відповідальний менеджер | Заявки, контроль місцезнаходження, польова інвентаризація |
| Відділ адміністрування продажів | Планування передачі, документи, взаємодія зі складом |
| Менеджер із трейд-маркетингу | Дані про місцезнаходження, щомісячний контроль, ремонт, інвентаризація |
| Склад | Зберігання та фізичне відвантаження |

Демо-доступ: на екрані входу можна увійти будь-якою роллю в один клік
(пароль для всіх демо-облікових записів — `demo1234`).

## Запуск

Портал не потребує складання (build) — це статичні файли з ES-модулями.

```bash
# з кореня репозиторію
python3 -m http.server 8080
# відкрити http://localhost:8080/equipment-portal/
```

> Відкриття через `file://` не працює: ES-модулі, service worker і камера
> потребують `http(s)`. Для роботи камери та геолокації на реальному пристрої
> потрібен **HTTPS** (або `localhost`).

Публікація: будь-який статичний хостинг (GitHub Pages, IIS, nginx) — достатньо
скопіювати каталог `equipment-portal/`.

## Встановлення мобільної версії

**Android (Chrome):** меню «⋮» → «Встановити застосунок».
**iOS (Safari):** «Поділитися» → «На екран „Домівка“».

Після встановлення застосунок відкривається без адресного рядка, має власну
іконку, працює офлайн і отримує доступ до камери та геолокації після
підтвердження системного запиту. Розділ **«Положення та процес» → «Мобільна
версія»** показує, які функції підтримує конкретний пристрій.

### Нативні збірки (за потреби публікації в Google Play / App Store)

Портал упаковується в нативну оболонку без переписування коду:

```bash
npm i -D @capacitor/cli @capacitor/core @capacitor/camera @capacitor/geolocation
npx cap init "Облік ТО" ua.truskavetska.eqportal --web-dir=equipment-portal
npx cap add android && npx cap add ios
npx cap sync
```

Точка розширення для нативного сканера позначена коментарем у
`js/scanner.js` — там достатньо підключити `@capacitor-mlkit/barcode-scanning`,
щоб отримати апаратне розпізнавання й на iOS.

```
    ├── seed.js                демонстраційний набір даних
    ├── auth.js                автентифікація та перевірка прав
    ├── workflow.js            бізнес-логіка процесу (усі зміни статусів)

```

## Поточні обмеження та інтеграція з BAS

Ця версія — **функціонально повний пілот на локальному сховищі**: дані зберігаються
в браузері пристрою (`localStorage` + `IndexedDB` для фотографій), тому кожен
пристрій має власну копію. Перед промисловою експлуатацією потрібні:

1. **Серверна частина та спільна база даних.** Увесь доступ до даних ізольовано
   в `js/store.js` (`all/get/insert/update/remove`), а бізнес-операції — у
   `js/workflow.js`. Заміна локального сховища на REST API до BAS не зачіпає
   інтерфейс.
2. **Серверна автентифікація.** Зараз пароль перевіряється на клієнті
   (SHA-256 у `js/auth.js`) — це прийнятно для пілота, але в продуктиві
   автентифікацію слід винести на сервер або підключити SSO (Microsoft Entra ID
   чи обліковий запис BAS). Точки заміни: `login()` та `hashPassword()`.
3. **Синхронізація з BAS** як єдиною системою обліку (п. 6.3): обмін довідниками
   (ТО, контрагенти, склади) і документами (Акти, переміщення, списання).
4. **Розсилка e-mail/пуш-сповіщень** для щомісячного звіту (п. 8.1) — зараз
   сповіщення відображаються всередині порталу.

Резервна копія у форматі JSON (Адміністрування → Дані) дозволяє перенести
накопичені дані пілота в майбутню серверну версію.
